# 终端界面与策略严苛验证（v2）

> 这次改动的两个目标：
> 1. 把前端从「能看」升级成「能快速做决定」的终端；
> 2. 把「回测赚钱」升级成「先证明样本外、扣完成本、扣完延迟、扣完死币折价之后还赚钱」。

---

## 1. 前端：参考 Axiom / Photon / GMGN 的信息架构

顶尖 Solana 终端（2026 年的 Axiom、GMGN、Photon）虽然风格不同，信息架构高度一致：

| 区域 | 作用 | 本项目对应 |
|---|---|---|
| 顶部 | 全局搜索、连接状态、账户/持仓、导航 | 顶部栏 + `/` 快捷键搜索 |
| 左列 | 发现：热门、新币、临近毕业、已毕业 | 「市场」面板 + 四个 Tab |
| 中列 | 图表是第一优先级，下面是持仓/成交 | Canvas K 线 + 持仓 + 最近成交 |
| 右列 | 交易/评分/风险，紧贴图表 | 评分证据、纸面测算、策略验证、聪明钱 |

设计取舍：

- **不做霓虹堆叠**：只用一套蓝色强调 + 绿/红语义色；数据密度靠排版，不靠发光。
- **每个数字都有单位**：SOL、%、x、分钟；未知字段显示 `—`，不伪造 0。
- **首屏就要能回答问题**：现在市场热不热、这个币能不能碰、策略现在能不能投钱。
- **K 线必须能处理脏数据**：单点、全平、只有 2 根 K 线都不能画出占满屏幕的色块。
- **响应式**：≥1240px 三列；1080px 以下左+中、右列下移；780px 以下单列。

### 1.1 启动

```bash
npm run server -- --port 8787 --db data/meme.db
# 打开 http://127.0.0.1:8787/
```

前端是零构建的 `web/index.html` + `web/style.css` + `web/app.js`，服务端直接读文件，改完刷新即可。

### 1.2 新增/增强的 API

| 路由 | 用途 |
|---|---|
| `GET /v1/overview` | 顶部 KPI、市场 1h 汇总、持仓估值、最后信号、验证结论 |
| `GET /v1/market/rank` | 热门榜：1m/5m/1h/24h 涨跌、成交量、sparkline、曲线进度、排序/搜索 |
| `GET/POST /v1/trenches` | 新币 / 临近毕业 / 已毕业 |
| `GET /v1/token/info` | 单币详情：1h 统计、峰值、年龄、stale、曲线储备 |
| `GET /v1/token/kline` | 1m/5m/15m/1h K 线 |
| `GET /v1/token/trades` | 最近成交 |
| `GET /v1/token/security` | 未知安全字段返回 `null`，不伪造「安全」 |
| `GET /v1/signals` | 信号 + 代币元数据 + 当前市值 |
| `GET /v1/positions` | 持仓 + 当前市值 + 浮盈亏 + 峰值倍数 |
| `GET /v1/validation/latest` | 验证报告（`?compact=1` 只取摘要） |
| `GET /v1/strategy` | 规则 id/权重/veto + 策略版本 |
| `GET /v1/search` | 代币/合约搜索 |

所有聚合接口有 2–5 秒 TTL 缓存；前端轮询不会把 SQLite 打爆。

## 2. 策略验证：为什么之前那套不算「验证」

旧回测有几个会系统性高估收益的假设：

1. 信号出现的那一笔成交立刻成交（没有延迟）；
2. 离场触发时立刻按当前价成交（没有延迟）；
3. 死币可以按最后价格无限期卖出（没有流动性折价）；
4. 回测结束时还持仓，假装按最后价平仓；
5. 只跑一段数据，然后反复调 TP/SL 看哪个最好（过拟合）；
6. 只看胜率/总收益，不看置信区间、随机基线、参数平原、规则多重检验。

新验证器 `src/validate.ts` 逐条修掉：

| 检查 | 做法 | 不通过的含义 |
|---|---|---|
| 数据审计 | 有效成交分钟、最长中断、币覆盖率、脏数据、价格跳变 | 数据本身不能用来下结论 |
| Walk-forward | 按成交事件数切 4 折，每折独立样本外，前期数据只做特征热身 | 只在某一折赚钱 = 不稳定 |
| 成本压力 | 2x 手续费 + 400bps 滑点 + 10s 延迟 | 真实摩擦一上来就亏 = 不能实盘 |
| 极端压力 | 3x 手续费 + 800bps 滑点 + 30s 延迟 | 同上 |
| 延迟敏感性 | 0s / 3s / 10s / 30s | 策略靠手速，不是靠 edge |
| 死币折价 | 离场触发后 15 分钟无成交 → 按 50% 报价出清 | 不折价会高估收益 |
| 数据结束清算 | 未平仓按 50% 报价清算 | 不能假装最后价能卖掉 |
| Cluster bootstrap | 按币种重采样 2000 次，给期望/胜率/PF 的 95% CI | 置信下界 ≤0 = 可能是运气 |
| 随机入场基线 | 同样的离场/资金/成本/延迟，只把选币换随机 | 策略跑不过随机 = 收益来自 beta |
| 参数平原 | TP/SL/持仓时间网格，看正期望比例和中位数 | 只有一个参数点赚钱 = 曲线拟合 |
| 规则 FDR | 6 条规则同时检验，BH 校正 q 值 + lift | 没有显著规则 = 评分是噪声 |

### 2.1 判定等级

| 结论 | 含义 |
|---|---|
| `INSUFFICIENT_DATA` | 样本不够，不能下「有效」或「无效」的结论；禁止投钱 |
| `NO_GO` | 样本够但硬门槛失败；禁止投真钱 |
| `PAPER_ONLY` | 基本门槛过了，但未达到 7 天 / 100 笔实盘样本；只能纸面 |
| `GO_LIVE` | 所有门槛通过；仍应先极小资金 + 保留 HALT |

### 2.2 硬门槛（全部通过才可能是 GO_LIVE）

1. 有效成交 ≥ 24h（实盘门槛 168h）
2. 平仓 ≥ 30 笔（实盘门槛 100 笔）
3. 信号 ≥ 30 条
4. cluster bootstrap 单笔期望 95% CI 下界 > 0
5. 盈亏比 ≥ 1.20
6. 最大回撤 ≤ 25%
7. ≥50% 的样本外折盈利
8. 2x 费 + 400bps 滑点 + 10s 延迟下期望 > 0
9. 10s 延迟下期望 > 0
10. 策略期望 > 随机入场期望
11. ≥50% 参数组合正期望且中位 > 0
12. ≥1 条规则 q<0.1 且 lift>1.2

### 2.3 运行

```bash
# 快速（参数网格小）
npm run validate:quick

# 完整（4 折 + 18 组参数 + 2000 次 bootstrap）
npm run validate

# 指定数据/折数
node src/validate.ts --db data/meme.db --folds 5 --min-hours 24

# 产出
#   data/reports/validation-<timestamp>.json
#   data/reports/validation-latest.json   ← 前端读取
```

## 3. 当前数据的真实结论（2026-10-18）

最新报告：`data/reports/validation-latest.json`

- 有效成交约 **1.3 小时**（首尾跨度 2.2h，中间有 **111 分钟采集中断**，覆盖率约 30%）
- 平仓样本 **23 笔**，低于 30 笔的最低门槛
- 结论：**INSUFFICIENT_DATA**，不能下「策略有效/无效」的结论
- 但已经可以确认的坏消息：
  - 样本外期望为负，95% CI 下界为负
  - 盈亏比约 0.8，最大回撤约 35%
  - 随机入场基线反而更好
  - `momentum` / `accel` / `velocity` / `early` / `concentration` 的 lift 显著小于 1（多数 q<0.05）
  - 只有 `demand` 不显著、也没有正 lift；没有任何规则通过 FDR
  - 验证器会输出「规则/下一步建议」，明确说先删/重做反向规则，不要在 0.5 小时数据上调参

**这意味着：当前策略不应投入真钱，也不应该在这 0.5 小时数据上继续调参。**
正确的下一步是让采集器连续跑满 7 天，再重新验证；如果规则仍然反向，就重做规则，而不是改 TP/SL。

## 4. 数据质量修复

本次同时修了一个会永久丢元数据的 bug：

- `trades.mjs` 会先用「首笔成交」建一条占位 `tokens` 行；
- 旧 `ingest.mjs` 的 `ON CONFLICT DO NOTHING` 会把随后到达的真实 `create` 事件丢掉；
- 结果：代币名字、创建者、创建时间永久为空。

现在改为 `ON CONFLICT DO UPDATE`，只补空字段，并把 `created_at` 取更早的值。
**需要重启采集器才会生效**：

```bash
# 停掉旧采集总控（会连同 ingest/trades 一起退出）
kill -TERM <collect_pid>
# 重新启动
nohup node --no-warnings src/collect.mjs >> data/collector.log 2>&1 &
```

历史里已经丢掉的名字无法从本地库恢复；新创建的币会正常补齐。

## 5. 建议的下一步（按顺序）

1. 让 `collect` 连续跑 **7 天**，不要中途重启（重启会丢订阅状态，但数据不会丢）。
2. 每天跑一次 `npm run analyze` 和 `npm run wallets`，看规则 lift 是否稳定。
3. 7 天后跑 `npm run validate`：
   - 如果 `INSUFFICIENT_DATA` → 继续采；
   - 如果 `NO_GO` → 按规则 FDR 报告删掉反向规则，做 v2；
   - 如果 `PAPER_ONLY` → 纸面小额跑 2 周；
   - 只有 `GO_LIVE` 才考虑极小资金实盘。
4. 实盘前必须确认：
   - `data/HALT` 开关可用；
   - 下单前签名落库；
   - 重启对账通过；
   - 有独立的余额/仓位对账告警。

## 6. 已知边界（报告里也会写）

- 曲线数学不等于真实成交：MEV、区块竞争、RPC 失败、交易失败重试都没有完整建模。
- 只覆盖本地采集器订阅到的 mint；没有成交的币不在样本里。
- walk-forward 各折是独立资金账户，没有模拟跨折资金曲线。
- 规则显著性使用「前向峰值」而不是可实现收益；q 值只用于排序和预警。
- 参数敏感性在全样本上做，只用于判断「是否只在一个参数点赚钱」，不能替代样本外验证。
- 当前数据只有约 0.5 小时有效成交，不能覆盖冷清/狂热/迁移潮等不同市场状态。
